# Pathfinder — Database Design & Schema Architecture

This document maps out the relational database layout for the Pathfinder MVP. The system utilizes **SQLite** to manage user profiles, skills, career paths, and the final analytical verdicts generated by the engine.

---

## 🗺️ System Data Flow & Schema Architecture

The database serves as the central memory of Pathfinder. It decouples user-submitted frontend data from the downstream analytical evaluation engines (**Reality Engine** and **Career Verdict Engine**).

## 🗂️ Table Specifications

### 1. `users`
Stores the core academic and commitment profile of the student. The downstream matching engines rely heavily on the timeline metrics to calculate learning feasibility.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `user_id` | `INTEGER` | Unique ID for the user (Primary Key) |
| `name` | `TEXT` | Full name (e.g., `"Punyadeep"`) |
| `education` | `TEXT` | Degree type (e.g., `"B.Tech"`) |
| `branch` | `TEXT` | Stream or specialization (e.g., `"Data Science"`) |
| `current_year` | `TEXT` | Current college year (e.g., `"3rd Year"`) |
| `cgpa` | `REAL` | Grade point average (e.g., `7.92`) |
| `experience_years` | `REAL` | Prior industry experience in years (e.g., `0`) |
| `timeline_months` | `INTEGER` | Target job deadline in months (e.g., `6`) |
| `learning_hours_week`| `INTEGER` | Weekly learning dedication commitment (e.g., `15`) |
| `created_at` | `TIMESTAMP`| Automatically tracks when the profile was generated |

---

### 2. `user_skills`
Stores user competencies. Instead of cramming strings like `"Python, SQL"` into a single row, this normalized structure maps one user to many independent skill rows for clean query operations.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `skill_id` | `INTEGER` | Unique ID for the skill row (Primary Key) |
| `user_id` | `INTEGER` | Links back to the user row (Foreign Key) |
| `skill_name` | `TEXT` | Name of the tool or skill (e.g., `"Python"`) |
| `proficiency` | `TEXT` | Self-assessed skill level (e.g., `"Intermediate"`) |

---

### 3. `user_preferences`
Tracks what domains a user actively wants to pursue or completely avoid. The Reality Engine uses these flags to quickly skip mismatched career choices.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `preference_id` | `INTEGER` | Unique ID for the preference rule (Primary Key) |
| `user_id` | `INTEGER` | Links back to the user profile (Foreign Key) |
| `preference_type` | `TEXT` | Categorizes choice direction (`"Positive"` or `"Negative"`) |
| `preference_value`| `TEXT` | The targeted sector or discipline (e.g., `"DevOps"`) |

---

### 4. `roles`
The primary catalog containing corporate job profiles evaluated by Pathfinder. It acts as the industry benchmark dataset for matching.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `role_id` | `INTEGER` | Unique ID for the job profile (Primary Key) |
| `title` | `TEXT` | Career job title (e.g., `"Data Analyst"`) |
| `minimum_experience`| `REAL` | Baseline industry experience required for entry |
| `average_salary_lpa` | `REAL` | Average market compensation package (e.g., `6.5` LPA) |
| `market_demand_score` | `INTEGER` | Industry demand index score (out of 100) |
| `competition_score` | `INTEGER` | Field competition/difficulty score (out of 100) |
| `prep_months` | `INTEGER` | Average time needed to reach readiness from scratch |

---

### 5. `role_skill_map`
A mapping table connecting target career roles to their respective required tools. This layout establishes a true **Many-to-Many** mapping architecture alongside the `user_skills` grid.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `mapping_id` | `INTEGER` | Unique ID for the mapping node (Primary Key) |
| `role_id` | `INTEGER` | Links to the targeted career role profile (Foreign Key) |
| `skill_name` | `TEXT` | Name of the associated technology tool (e.g., `"SQL"`) |
| `importance` | `TEXT` | Priority ranking modifier (`"Required"` or `"Preferred"`) |

---

### 6. `career_verdicts`
Stores the final diagnostic evaluation calculated by the **Career Verdict Engine**. It archives calculated match results, missing dependencies, and baseline timelines.

| Column Name | Data Type | Description / Example |
| :--- | :--- | :--- |
| `verdict_id` | `INTEGER` | Unique ID for the generated verdict (Primary Key) |
| `user_id` | `INTEGER` | Links to the evaluated user (Foreign Key) |
| `role_id` | `INTEGER` | Links to the target career option profile (Foreign Key) |
| `skill_match` | `INTEGER` | Parity score measuring existing skills against the role (e.g., `92%`) |
| `timeline_match` | `INTEGER` | Evaluation score matching user availability against prep time |
| `final_score` | `INTEGER` | Overall structural composite engine score (e.g., `89%`) |
| `verdict` | `TEXT` | System recommendation classification state (`"Recommended"`) |
| `reasons` | `TEXT` | Text summary explaining positive factors |
| `risks` | `TEXT` | Text summary pinpointing skills gaps or career risks |
| `created_at` | `TIMESTAMP`| System timestamp capturing exactly when this score was run |

---

## 💡 Normalization Focus & Core Design Benefits

*   **Atomic Columns:** Skills and preferences are isolated away from the root user table. This design approach completely avoids messy string search lookups like `LIKE '%SQL%'` on comma-separated textual lists, allowing for clean database operations.
*   **Decoupled Matching Logic:** Storing technologies individually inside `user_skills` and `role_skill_map` enables the underlying algorithms to execute lightning-fast relational operations directly inside SQLite instead of pulling bloated tables into memory.
